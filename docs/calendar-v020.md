# v0.2.0 日历导入与订阅

## 在当前 GitHub 网站导入本地日历

进入“我的任务”或“时间安排”，点击“导入 / 订阅日历”。默认“导入本机日历”会在浏览器生成 CampusFlow-calendar.ics。打开或分享给日历程序，按照面板中的 iPhone、Windows 步骤完成导入。

日期明确的未完成任务均导出为 VEVENT，因此截止任务也能出现在常见日历中。“【截止】”为透明时间点，不虚构工作时段；只有日期时使用全天事件及排他的次日结束日期。定时活动保留开始与结束时间。提前提醒默认关闭，只给明确时刻的任务写入可选 VALARM。能否提醒、何时提醒仍取决于日历客户端权限与支持情况。

这是一次性快照。再次导入可能产生重复；建议建立单独的 CampusFlow 日历。通知原文、引用依据与日志不会写入兼容日历文件。JSON 备份仍用于完整迁移，“原格式 ICS”保留原有 VEVENT/VTODO 行为。

## 持续订阅需要独立服务

GitHub Pages 不能处理 POST/PUT，也不能保存个人快照。因此不会生成虚假的 blob/data 订阅地址，更不会把所有人的个人日历上传到公开 GitHub 仓库。当前静态站的订阅入口需要用户填写实际部署的 CampusFlow HTTPS 服务根地址；本次没有创建公开服务或上传任何个人任务。

源码包含两种运行方式：`npm run dev` 的本机服务同时支持网页、AI 和订阅；`npm run calendar:serve` 仅运行日历接口（不依赖 Vite 运行时）。后者默认监听 127.0.0.1:8787，部署时设置 HOST、PORT，并使用 HTTPS 反向代理及持久磁盘。

环境变量：

- `HOST`：独立日历服务监听地址，公开反向代理部署通常为 0.0.0.0。不要把本机开发服务直接暴露到公网。
- `PORT`：独立服务默认 8787，本机开发服务默认 5173。
- `CAMPUSFLOW_CALENDAR_DIR`：持久数据目录，默认 .campusflow-calendars，不得加入公开源码。容器部署需要持久卷；备份该目录也包含订阅内容和管理密钥的哈希。
- `CAMPUSFLOW_CALENDAR_ORIGINS`：允许连接的前端 Origin，逗号分隔，默认 https://hiro-bo.github.io。不使用通配符；本机开发服务额外允许其 localhost/127.0.0.1 Origin。

在网页的“持续订阅”页填写服务根地址，核对范围后勾选同意，点击“连接并创建订阅”。可复制只读 HTTPS 地址，或点击“在日历 App 中订阅”。iPhone 在日历列表添加订阅；Outlook 选择“从 Web 订阅”。本机 localhost 地址只供当前电脑访问，不能直接给 iPhone 使用。

## 同步与隐私

只上传名称、类型、日期、地点、状态及提醒设置，不上传通知原文、证据和日志。独立的随机读取标识与管理令牌均使用 256 位随机值；服务端仅存管理令牌的 SHA-256 哈希，不提供订阅列表接口。任何持有只读地址的人均可读取日历。管理令牌仅保存在当前浏览器，不进入任务备份与操作日志。

网站打开时，任务更改会防抖后上传；刷新后恢复连接并上传当前任务。日历软件自行轮询，不能保证实时。完成、删除或清空任务会让相应 UID 从快照消失，客户端实际移除的时间取决于其刷新行为。日历内编辑不会反向写回网站。提醒设置会在此浏览器保留。

点击“撤销此订阅地址”删除服务器记录；再次访问返回 404。原本已下载/导入的副本不会被远程删除，需要在日历 App 移除。清理网站数据之前先撤销，否则管理权限可能丢失。当前不支持多标签页协调、账户恢复或多浏览器同时管理同一订阅；以一个浏览器作为任务来源。

服务限制：单份 1000 个任务、请求体 1MB、单进程最多 1000 个订阅、每 IP 每分钟 60 次写请求。文件存储适合小规模单实例；不适合多个实例同时写同一目录。要面向大规模公开用户，需要进一步做账户体系、共享限流和容量管理。

自动测试覆盖格式、时区、全天跨年、截止事件、提醒、转义折行、数据最小化、持久化、鉴权、CORS、修改与清空、撤销及更新撤销并发；通过真实本机 HTTP 验证接口。Windows 与 iPhone 日历真机导入、客户端轮询和系统提醒仍需用户亲测，不将自动化测试视为真机结果。
